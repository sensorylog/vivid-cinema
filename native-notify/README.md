# Vivid Cinema — web push with Native Notify

_Updated by Agent Notify (web push add-on). App id 33997; the publishable web key lives in
`native-notify/web/nativeNotifyIds.js`._

Vivid Cinema delivers **browser push** through Native Notify's universal service. The
browser registers itself directly with Native Notify — there is no Cloud Function, no
Firebase Blaze plan, and no APNs/FCM credentials involved for the web.

## How it is wired

- `native-notify/web/nativeNotifyIds.js` — the app id and the **publishable** web key.
  Both are public by design (the web key can register one browser and read that browser's
  own inbox; it can never send). Nothing to configure in Firebase Hosting, no environment
  variables. The app **token** is never in website code.
- `native-notify/web/native-notify-web-push.js` — the registration client
  (`enableNativeNotifyWebPush`, `ensureNativeNotifyWebPush`, `disableNativeNotifyWebPush`,
  `getWebPushState`). It asks Native Notify for the app's VAPID **public** key at subscribe
  time, so a rotated key is picked up automatically — the key is never hardcoded.
- `service-worker.js` — the site's existing root worker now handles Native Notify pushes.
  A site may have only **one** service worker per scope, so the push listeners were added
  to Vivid's own worker instead of registering a second one; caching, the update flow and
  the notification-click behaviour are unchanged. Both payload shapes are accepted:
  Native Notify's `{title, body, image, tag, data:{url}}` and the legacy reminder senders'
  `{title, body, tag, url}`.
- `scripts/push-notifications.js` — `enableCinemaPush()` and `ensureCinemaPush()` register
  through Native Notify with `serviceWorkerPath: "/service-worker.js"`. The existing
  **Enable** button in the release-alerts popover and the news reminder buttons call it, so
  the browser registers only after the visitor clicks. `ensureCinemaPush()` runs on page
  load and re-registers silently — no prompt — for browsers that already allowed
  notifications.
- `firebase.json` — the CSP `connect-src` now allows `https://app.nativenotify.com`.
  Without it the browser blocks both the key fetch and the device registration.
- `public/native-notify-sw.js` — generated by the add-on but **not registered** (Vivid uses
  its own `service-worker.js`). Leave it alone; do not register it.

## Scheduled cinema reminders and release alerts

The two GitHub Actions workflows are **unchanged**:

- `.github/workflows/cinema-reminders.yml` → `automation/send-cinema-reminders.mjs`
- `.github/workflows/release-alerts.yml` → `automation/send-release-alerts.mjs`

They still send with the legacy `web-push` + `pushSubscriptions` flow. They were not
rewritten because the **Native Notify send API is not documented anywhere available to
this workspace**: nothing in the repository or in the integration guide states the
endpoint, its authentication (an app token is a send-capable credential and would have to
become a new Actions secret) or its payload/targeting format. Guessing it would silently
break scheduled delivery.

What is missing before those senders can move to Native Notify:

1. The documented HTTP endpoint for sending a push to a universal app (all devices, a
   subscriber id, or a group), and its exact request body.
2. The authentication method for that endpoint, and whether a send-only key exists (so the
   app token itself never has to leave the dashboard).
3. A documented per-subscriber targeting field, so a reminder can go to one user's registered
   browsers (the senders currently read `users/{uid}/pushSubscriptions`).

Until then, scheduled messaging is available from the Native Notify dashboard
(**Push notifications → Scheduling**). Note that a browser can hold only one push
subscription: a browser that clicks Enable here moves to Native Notify's key, so the legacy
senders will find its old `pushSubscriptions` endpoint revoked (their next run deletes the
dead record on the 404/410 response, which is expected). Reminders already stored in
`users/{uid}/cinemaReminders` and its in-app timer keep working — only the legacy
background delivery to that browser stops.

## GitHub Actions secrets

No new secret is required by this change. The existing workflows keep using:

- `FIREBASE_SERVICE_ACCOUNT_JSON`
- `VAPID_PRIVATE_KEY`

No Native Notify token belongs in GitHub Actions while the senders stay as they are.

## Native Notify dashboard settings

- **Nothing to paste for web push.** The publishable web key is already committed in
  `native-notify/web/nativeNotifyIds.js`; the VAPID public key is fetched by the browser.
- No Firebase service-account key and no Apple `.p8` are needed for web push (those are
  only used for the Android and iPhone apps).
- Regenerated the web key in **Native Notify → Keys**? Ask Agent Notify to update
  `NN_WEB_KEY` in `native-notify/web/nativeNotifyIds.js`.

## Verify background notifications

1. Deploy the site (Firebase Hosting) — the CSP header change ships with it.
2. Open https://vivid-cinema.web.app/ in Chrome or Edge, open the release-alerts popover and
   click **Enable**, then choose **Allow**.
3. Check the registration landed: DevTools → Application → Service Workers shows
   `/service-worker.js` active, and Console shows no CSP error for `app.nativenotify.com`.
   In Native Notify the device count under this app should go up.
4. Lock the screen or switch to another tab/window, then send a real push (ask Agent Notify
   for a test send, or send from the dashboard).
5. Tap the notification: it opens the page in `data.url` (or the site home).

If nothing appears, check the machine before the code: the OS must let the browser notify
(macOS System Settings → Notifications → your browser; Windows Settings → System →
Notifications and Focus off) and the browser must allow the site (Chrome: tune icon →
Notifications → Allow).
